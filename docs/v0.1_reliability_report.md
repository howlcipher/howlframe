# HowlFrame v0.1 Reliability Report

## Overview
HowlFrame has reached its v0.1 release-candidate baseline. This milestone marks the transition from a conceptual interpreter to a fully hardened, standalone compiler and virtual machine ecosystem. 

A reader evaluating HowlFrame v0.1 should quickly understand the following facts about the architecture:
1. **`.howl` is a real source language**, featuring a semantic checker, type inference, and validation passes.
2. **HowlFrame has a compiler** that lowers `.howl` source into HowlFrame Intermediate Representation (HFIR).
3. **`.howl` can compile to standalone `.hfbc`** (HowlFrame Bytecode), a versioned and checksummed binary artifact format.
4. **`.hfbc` executes on the HowlFrame VM**, a secure standalone runtime that enforces execution budgets and capability boundaries.
5. **Go generation is another backend**, alongside Wasm and JavaScript, but standalone bytecode is a primary, fully isolated target.
6. **Native x86/ARM compilation is not currently claimed.**

## Hardening and Reliability Audits
During the v0.1 hardening phase, the following guarantees were audited, tested, and structurally enforced:

### 1. Artifact Integrity
Bytecode compilation now produces a secure binary envelope (`.hfbc`) containing:
- Magic bytes (`HFBC`) to prevent misinterpreting arbitrary files.
- A format version integer to prevent backward/forward compatibility drifts.
- A 32-byte SHA-256 checksum to ensure the artifact has not been truncated or tampered with.
- The `gob`-encoded bytecode payload.
**Status**: The VM strictly validates the checksum before attempting to decode or execute the payload, returning structured errors on corruption.

### 2. Execution Policy and Budgets
The standalone VM enforces deterministic instruction limits on untrusted execution.
- By default, execution is capped at 100,000 instructions.
- The CLI `-run-bc` flag accepts a `--max-instructions` override to bound execution predictably.
- Zero, negative, and malformed budget values fail-closed immediately.
**Status**: An infinite loop (e.g. `(while true ...)`) will deterministically panic with `LIMIT_EXCEEDED` once the budget is exhausted, preventing Denial of Service.

### 3. Capability Gating
Capabilities (`Network`, `Filesystem`, `Process`, `Environment`, `Database`) are strictly gated at the VM level, independent of the compiler.
- If a bytecode artifact attempts an operation without the corresponding `-allow-caps` flag, it panics with `CAPABILITY_DENIED` *before* the operation executes.
- The capability checks are unit-tested under adversarial conditions to ensure no operation bypasses the gate.
**Status**: A process running without `--allow-caps network` cannot use `fetch` or `http_server`, fully isolating untrusted proposals.

### 4. Malformed and Adversarial Bytecode
The runtime was subjected to malformed instructions, invalid type offsets, and missing references.
- All type assertions in the VM use safe type-switches (`v, ok := val.(string)`) rather than direct assertions, returning `VMError` (e.g., `TYPE_ERROR`) instead of a Go panic.
- `HFIR_UNBOUND_REF` false positives have been resolved; the semantic checker correctly fails the build for genuinely unbound variables, while legitimately dynamic variables proceed.

### 5. Deterministic Coverage
A machine-generated coverage matrix (`docs/reference/construct_coverage.md`) now tracks the authoritative capabilities of the runtime.
- Generates directly from the compiler's `internal/construct` registry.
- Tracks checker, HFIR, bytecode, VM, interpreter, and test support.
- Enforced in CI via a drift test.

## Conclusion
The HowlFrame v0.1 standalone runtime is structurally capable of executing untrusted AI and user proposals safely. It does not trust its input artifacts, it does not trust the source code's capabilities, and it does not trust the execution time. 

Application Dogfooding and the Release Authority demo confirm that HowlFrame can successfully power stateful CRUD applications, networked tools, and secure AI sandboxes entirely on the standalone VM.
