# HowlFrame v0.1 Project Status Report

## What exists today
HowlFrame is an experimental AI-native language and capability-bounded execution runtime. The `v0.1.0` release provides a compiled, standalone CLI binary (`howlframe`) supporting syntax parsing, type checking, HFIR verification, AST-to-Go transpilation, AST-to-JS transpilation, WebAssembly execution, and most importantly, a standalone Bytecode (HFBC) Virtual Machine.

## What v0.1 proves
- **Capability Gating**: Execution is strictly bounded by explicit runner-owned capability grants (`--allow-caps`). Attempting an unauthorized instruction safely panics.
- **Instruction Budgets**: A deterministic instruction limit (`--max-instructions`) halts infinite loops and enforces execution budget.
- **Determinism**: Untrusted AI proposals (JSON) can be evaluated by a deterministic trusted policy running as HFBC.
- **Artifact Isolation**: Compiled `.hfbc` artifacts execute completely outside the Go source tree with zero external dependencies.

## What v0.1 does NOT prove
- **OS-level isolation**: It is not a container or hypervisor.
- **Formal verification**: No cryptographic proofs or formal memory verification are provided.
- **Scale/Performance**: It focuses on semantic bounds over raw execution speed. 
- **Production maturity**: It remains experimental and expects breaking changes.

## Compiler/runtime pipeline
`howlframe check` -> Lexer -> Parser -> Semantic Type Checker -> HFIR Lowering -> HFIR Verification Gate -> `howlframe build` (Output: `.hfbc`) -> `howlframe run` (VM Execution).

## User experience
A streamlined subcommand interface (`check`, `build`, `run`) replaces the legacy flat flags for primary usage, significantly lowering onboarding friction.

## Release status
**v0.1 is fully released.** Tag `v0.1.0` is published on GitHub Releases, with standalone binaries and checksums for Linux, macOS, and Windows.

## Demonstrated use cases
- **Release Authority**: Trusted runner evaluating untrusted deployment proposals and persisting state.
- **Bounded Action Executor**: Untrusted LLM mapping intents to finite, runner-controlled filesystem actions.
- **CLI Tooling**: `todo_cli` and `kv_cli` utilizing the in-memory native store (`memory://...`).
- **HTTP Routing & Observability**: `status_api` generating robust Go endpoints.

## Known limitations
- Limited capability granularity (e.g., `filesystem` grants broad access, not directory-scoped).
- The Wasm and JS backends do not support all AI primitives that the Go backend does.
- Memory store persistence is strictly in-memory during the VM process lifetime (no durability).
- Missing random-access reads in Wasm collections.

## Highest-risk technical areas
- **Backend Drift**: Go, JS, VM, and Wasm targets require shared conformance testing to prevent semantic divergence.
- **VM Escape Vulnerabilities**: While logic-bounded, the VM process itself might have unhandled panics that bypass the capability envelope.

## Highest-value future directions
- Artifact versioning, signing, and hashing.
- Incremental compilation and HFIR patch deltas to reduce LLM token overhead when repairing code.

## Explicitly deferred work
- Teleological and fuzzy execution loops.
- Broad feature expansions lacking direct user evidence.
- LLVM native bindings (Wasm serves as the initial native boundary).

## What evidence should trigger v0.2 work
Any new major feature or v0.2 transition requires documented user friction, a proven capability gap in a real application deployment, or benchmark evidence demonstrating an LLM hallucination bottleneck. Momentum alone does not justify new syntax.
