# 2026-11-27: v0.4.0 release prep, and the consumer check that found #321

## Consumer evidence

HowlPlane checks itself against a new HowlFrame `main` before it moves its CI pin (HowlPlane improvements.md #86). Against #320 (`8ec5315`):

| Check | Result on `8ec5315` |
| --- | --- |
| `tests/test_tui_logic.py`: 32 replay cases over the committed TUI artifact | 31 failed. Every replay record had an empty view and no effects. |
| The live TUI suites: launcher, pty session, governed run and feasibility (52 tests) | passed |

* **Cause.** #320 replaced `[]any` VM lists with the persistent `*vmList`. The live `terminal_app` path (`apply`, `startProcess`) reads a handler's lists through `sliceFromList`. The replay recorder (`record`) still asserted `[]any`, so only lists built by `parse_json` came through.
* **Why HowlFrame's own tests missed it.** Its replay test apps build every list with `parse_json`.
* **Fix.** #321, merged as `e8f3349`, makes the recorder read lists as `apply` does. Its regression test, `TestTerminalReplayRecordsListLiteralViewsAndEffects`, builds the view and effects with list literals and fails without the fix.
* **After the fix.** HowlPlane passed against `e8f3349`: the replay suite 32 of 32, and the full suite 3143 passed. It moved its pin there (howlcipher/howlplane#230).
* **Lesson.** When the VM changes how a value is represented, every reader of handler results needs checking, recorders included. A test app that builds its values only one way can hide the change.

* **Version.** 0.4.0 in `howlframe.go` and in the CLI test that checks `version` and `help`.
* **Changelog.** `## v0.4.0 (prepared 2026-11-27; not yet tagged)` sits above the entries it releases.

## Compatibility evidence

* **Version reporting.** `howlframe version` prints `HowlFrame 0.4.0` and `HFBC format: 2`, and `help` names the 0.4.0 CLI. `interop --json` reports version 0.4.0, and its `run` command lists `--color` and `--replay`.
* **Artifacts built by v0.3.0** (the tag, `7318762`). Of the 49 `tests/*.howl` fixtures, 35 build as bytecode with v0.3.0. On v0.3.0 and on this tree, each produces byte-identical combined output with the same exit status:
  * 20 exit 0;
  * 14 fail the same way (no grants were given);
  * 1 server runs until the 10-second bound.
* **The other 14 fixtures do not build as bytecode with v0.3.0,** so they say nothing either way. Twelve use constructs the bytecode target does not compile (`struct`, `match`, `test`, `middleware`, `go_import`, `trace`). Two are module fragments that do not build on their own.
* **A `terminal_app`.** `examples/terminal_counter`, built by v0.3.0, gives identical line-mode output and exit status on both runtimes.
* **Gate results** for the final tree are in the pull request.
