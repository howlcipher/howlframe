### 3. Is the thesis sound?

**INFERRED — strongest argument for:** Small generated programs could compose transformations and conditional actions while letting deterministic machinery reject unsupported operations, limit execution and explain failures. HowlFrame already supplies several necessary mechanisms (`internal/construct/construct.go:25–42`; `internal/vm/vm.go:1937–1947`).

**INFERRED — strongest argument against:** The demos mostly prove that a *trusted fixed program* can interpret untrusted JSON. Action Executor’s safety comes substantially from hardcoded action and artifact allowlists (`apps/action_executor/action_executor.howl:54–119`). A Go service with schema validation could implement those rules.

The thesis earns a product only if generated composition provides measurable value over fixed tool calls without sacrificing control. Today that advantage is unproven.

### 4. Who would use it, for what job?

**INFERRED:** The initial user is an agent-platform developer needing bounded customer-specific automation: normalize records, filter evidence, calculate a decision, then request one approved action.

Alternatives are a fixed JSON action catalog, a Starlark script with narrow host functions, or a sandboxed conventional program. HowlFrame must win on integration effort, reviewability and safe composition—not language novelty.

**VERIFIED:** The existing executor already demonstrates logical artifact IDs and runner-owned approval (`apps/action_executor/action_executor.howl:68–99`). **INFERRED:** Use that as an onboarding exercise, but do not mistake release-marker simulation for demand for autonomous deployment.

### 7. How does it compare?

The external facts below are **VERIFIED from primary documentation**; product judgments are **INFERRED**.

| Alternative | Existing strength | HowlFrame’s plausible position |

### 10. What should authority become?

**INFERRED:** Evolve toward runner-issued resource handles and named action bindings, preserving existing grant names for compatibility.

Separate read/write authority, allowed environment keys, store namespaces, network destinations/methods and executable identities. Enforce filesystem containment against traversal and symlink escapes; network policy must survive redirects and address resolution.

Add wall-clock deadlines, byte limits, output limits, call counts and aggregate invocation budgets. **VERIFIED:** The current vocabulary only expresses five effect classes, with URI-dependent additional filesystem authority for stores (`internal/capability/capability.go:8–15`; `internal/capability/capability.go:46–58`).

**INFERRED:** Model calls need explicit effects covering provider/model, data disclosure, tokens, cost and retries. Model results remain untrusted data. Approval should bind artifact hash, action, target and expiry, with state preconditions checked at execution.

### 11. What does “verified” concretely mean?

**VERIFIED today:** Different gates mean different things. Adapter intake checks transport integrity and some type relationships; source checking runs semantic checks; bytecode loading checks its envelope and limited structure (`internal/hfir/model_adapter.go:616–628`; `howlframe.go:659`; `internal/bytecode/artifact.go:115–198`).

The production HFIR gate blocks only selected diagnostic codes. Its own comments explicitly disclaim full control-flow/cycle verification and general target feasibility (`howlframe.go:466–489`).

**INFERRED — statically checkable:** schema/version integrity, references, supported forms, types where known, stack/control layouts, declared action requirements and literal resource constraints.

**INFERRED — runtime-enforced:** dynamic resource scope, instruction/deadline limits, allocations, effect quantities, approvals, state preconditions and host failures.

**INFERRED — unclaimable:** intent correctness, model truthfulness, universal prompt-injection immunity, transactionality or production isolation. Say “passes verifier X, version Y, checks Z.” **VERIFIED:** Release Authority’s disclaimer already rejects production-security and formal-verification claims (`apps/release_authority/README.md:7–15`).

### 13. First falsifiable experiment

**INFERRED hypothesis:** An unfamiliar agent developer can integrate generated HowlFrame programs with less repair effort and equally strict authority control as Starlark with fixed host actions.

**Setup:** Three external developers; twenty small evidence-transformation and action-selection tasks each; identical model, prompts, host action catalog, hidden tests and two-repair ceiling. Include self-grants, path injection, malformed outputs, oversized inputs and partial-failure cases. Predefine tasks before generation.

**Metrics:** onboarding/integration minutes, behavioral success, repairs, unsupported requests, unauthorized effects and whether each receipt explains the actual outcome.

**Pass:** zero unauthorized effects; at least 90% behavioral success after two repairs; onboarding below one hour; at least 25% less median repair/review time than baseline.

**Kill/pivot:** any bypass blocks release. No measurable advantage favors a fixed-action proposal product over a new programmable runtime.

**Estimated cost:** five builder days, roughly twelve participant hours, and a capped $100 model budget. **VERIFIED:** Existing adapter evidence is a tiny stored-candidate sample, not broad provider reliability (`docs/hfir_model_adapter_status.md:35–43`).
