**Investigated and deliberately not filed (2026-08-29):** `BCInstruction.UnmarshalJSON`
(`internal/bytecode/bytecode.go:32-42`) discards `NameToOpcode`'s failure signal with
`inst.Op, _ = NameToOpcode(inst.OpString)`, which looks like a fail-open at the artifact
boundary. It is not reachable from product code: the durable artifact format is HFBC, which
`ReadArtifact` decodes with `gob` behind a magic check, a version check, a length bound and a
SHA-256 payload hash, and nothing in the repository JSON-decodes a `BCProgram`. The method is
latent, so it is recorded here rather than filed as a live bug.



### 50. `route` indexes a handler lambda it never validated, panicking the compiler
* **Symptom:** `(http_server 8080 (route "/" (lambda (req))))` — a lambda with an argument list but no body — crashes the compiler with `panic: runtime error: index out of range [2] with length 2` at `internal/checker/checker.go:422`, instead of reporting a checker error. Verified by running `howlframe -validate` on that source.
* **Root Cause:** `checkGoAppHandler`'s `case "route"` reads `handlerNode.Children[2].Children[1]` and `handlerNode.Children[2].Children[2]` without ever checking that `Children[2]` is a `List` of three children whose head is `lambda`. ### 25. `let` with more than one body statement infinite-recurses instead of erroring

### 46. Bytecode `try_let` re-executes its final branch instruction

* **Problem:** After `OpTryLet` runs its selected catch or success body, `internal/vm/vm.go` advances the enclosing instruction pointer by only the three embedded-body lengths. It omits the `OpTryLet` instruction itself, so the VM lands on and executes the final embedded instruction a second time.
* **Observed application need:** HowlFrame Repo Analyst must read every discovered text file inside a `for`, recover from an unreadable file with `try_let`, and continue aggregating results.
* **Current behavior:** The multi-module application validates and compiles to bytecode, but the second loop iteration fails with `{"phase":"runtime","code":"STACK_UNDERFLOW","function":"main","instruction":52,"opcode":"FOR_NEXT","message":"stack underflow at FOR_NEXT"}`. A reduced `for` plus `try_let` program reproduces the failure on either branch. The repeated final branch instruction consumes the two values that `FOR_INIT`/`FOR_NEXT` retain on the shared operand stack for the enclosing iterator.
* **Classification:** VM bug in an existing construct. This is not a new language, standard-library, runtime-capability, or tooling requirement.
* **General use case:** Any batch program that loops over fallible work needs this composition, including repository analyzers reading files, backup utilities copying entries, and data converters parsing records.
* **Semantics and effects:** A `try_let` evaluates its value instructions once, executes exactly one branch once, then resumes at the first instruction after all of its embedded instructions. The repair does not alter user-visible effects except to remove the unintended duplicate final effect and ensuing stack corruption.
* **Syntax, types, errors, and provenance:** No syntax or type changes. The fix removes the erroneous `STACK_UNDERFLOW`; existing nested-operation errors and source representation are unchanged.
* **Capability:** No capability change. `try_let` itself is capability-neutral; its value or branch instructions retain their existing capability checks.
* **HFIR and bytecode representation:** No checker, HFIR, verifier, lowering, opcode, or artifact-format change. The current `OpTryLet` representation already records value, catch, and success lengths correctly.
* **VM behavior:** Advance by `1 + value length + catch length + success length` before continuing the enclosing dispatch loop.
* **Interpreter parity:** The Phase 1 direct AST interpreter does not implement `try_let` or `read_file`, so adding a direct-interpreter oracle would expand this repair into a separate backend feature. The regression instead uses checker-valid source for both branches, and the full existing difftest remains the cross-backend regression gate.
* **Dependencies:** None. Improvement #95 is already Done and exposed this defect through the real multi-file application.
* **Acceptance criteria:** Success and catch branches each execute once inside a multi-iteration `for`; execution resumes after `try_let`; no iterator state leaks to output; no `STACK_UNDERFLOW` occurs; and Repo Analyst completes file aggregation through the standalone bytecode VM.
* **Required tests:** Focused VM regressions for both success and catch paths, followed by the Repo Analyst application proof and the Working Protocol verification suite.
* **Model routing:** `gpt-5.6-terra`; the defect is localized, fully reproduced, and has a one-line production fix plus focused tests.
* **Recommended execution mode:** `reviewed-edit`.
* **Status:** Done (2026-08-08). Journal: `docs/journals/2026-08-08_repo_analyst_dogfooding.md`.
  * **Root cause and fix:** The three stored region lengths exclude `OpTryLet` itself. Changed the post-branch advance from `valLen + catchLen + successLen` to `1 + valLen + catchLen + successLen`; no other VM behavior or representation changed.
  * **Regression evidence:** The focused success and catch tests were added first and both failed on the original VM with `STACK_UNDERFLOW`, after printing the leaked outer-loop index. Both use checker-valid HowlFrame source; the catch case performs a genuinely failing `read_file` with the filesystem capability. Both pass after the one-line repair.
  * **Application proof:** The five-module HowlFrame Repo Analyst application compiles with `-compile-bc` and runs with `-run-bc` using only `process,filesystem`. Its end-to-end fixture proves classification, text reads, TODO/FIXME counting, aggregation, deterministic structured output, optional file output, explicit application exits, and capability denial without generated Go or JavaScript.
  * **Verification:** `go test ./internal/vm -run '^TestBytecodeTryLetResumesAfterEmbeddedInstructionsInFor$' -count=1`; `go test ./internal/bytecode ./internal/vm`; `go test ./examples/repo_analyst -run '^TestRepoAnalystStandaloneBytecode$' -count=1 -v`; `go test ./...`; `go vet ./...`; `go build -o /tmp/howlframe-dogfood-final howlframe.go`; difftest 17 passed / 27 skipped / 0 failed; `gofmt -l .`; `git diff --check`.
  * **Benchmark gate:** Not applicable. The production diff changes only bytecode-VM instruction-pointer control flow for `try_let`; it does not touch the `defun`/`type_hint`, `read_file`, `str_split`, or `test` writing surfaces and cannot change transpiler output.

### 48. `parse_json req.body` reads unbounded request data and ignores read errors

* **Problem:** The standalone bytecode VM's `OpParseJson` special case for
  `req.body` calls `io.ReadAll(req.Body)` with no size limit and discards the
  returned error before parsing and restoring the body.
* **Evidence:** `internal/vm/vm.go` performs the read in the request-body
  branch. The limitation was independently recorded in
  `docs/journals/2026-08-13_external_consumer_v011.md`.
* **Risk:** A remote request can consume unbounded memory. A partial or failed
  read can be interpreted as normal input, giving callers an unreliable error
  boundary.
* **Scope:** Add an explicit bounded body-size policy and deterministic
  read-error handling with focused VM request-body tests. This must be a
  separate change from HFIR semantic repair.
* **Done (2026-08-18):** Bounded request body reads to 10MB using `io.LimitReader` in `internal/vm/vm.go` and added explicit handling for read errors and oversized payload limits. Added comprehensive unit tests in `internal/vm/request_body_test.go` (`TestBytecodeParseJSONRequestBodyLimitsAndErrors`) testing simulated read failures and oversized payloads.
