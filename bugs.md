## Details

### 1. Lexer panics on EOF during unterminated string
In `zero.go`, the string lexer currently scans for the next quote. If EOF is hit, it correctly calls `reportError`, but if the file is truly truncated, we should ensure no other routines attempt to consume past the array bounds. The code is mostly safe but needs explicit unit tests to guarantee it never panics outside of the controlled JSON error output.

### 2. Python Orchestrator timeout with heavy models
When running `orchestrator.py` against a local Ollama instance with a large model (e.g. 70B parameters), the structured generation engine in `outlines` might hang for a long time compiling the regex/grammar. We need to add logging or a loading indicator so the user knows the compilation/generation hasn't silently frozen.

### 6. Include Paths Relative to File
* **Description:** `(include "file.zero")` uses `os.ReadFile(filename)`.
* **Why:** If the zero compiler is run from a different directory, it will fail to find relative included files.
* **Impact:** 6/10 (High).

### 7. defun Typing Rigidness
* **Description:** `defun` maps all arguments to strings in Go.
* **Why:** We cannot cleanly pass `req` to helper functions without using strings.
* **Impact:** 7/10 (High).

### 8. try_let Error Interception Rigidness
* **Description:** `try_let` only intercepts `parse_json` right now.
* **Why:** Needs to generalize to any function returning `(value, error)`.
* **Impact:** 5/10 (Medium).

### 9. Depth Limit Crash via `let` Chaining
* **Description:** Every `let` block increments the AST depth (`depth+1` at line 644). If an AI generates a long sequential script with 1,000 variable assignments, the transpiler crashes with `AST too deep`.
* **Why:** Variable scope needs to be flattened instead of infinitely nesting in AST.
* **Impact:** 8/10 (High).

### 10. String Escaping Limitations
* **Description:** The lexer only supports `\n` and `\t`. It breaks on unicode escapes (`\uXXXX`) and escaped single quotes (`\'`).
* **Why:** LLMs frequently output these escapes, especially in JSON strings.
* **Impact:** 7/10 (High).

### 11. No Runtime Source Mapping
* **Description:** Runtime panics point to `main.go`, not the `.zero` file.
* **Why:** The transpiler should inject Go `//line filename.zero:line` directives so runtime panics map back to the AI's code.
* **Impact:** 6/10 (Medium).

### 12. Lexer cannot tokenize `!=`
* **Description:** `lexer()` in `zero.go` accepts `=`, `<`, `>`, `+`, `-`, `*`, `.`, `/`, `_` as symbol start/continuation characters (~line 140), but not `!`. Any `.zero` source containing `!=` fails at the lex stage with `Unexpected character: !`, before the parser is ever reached — even though `generateStatement`'s `if`/`match` condition handling (lines ~830, ~930) explicitly checks for and supports an `"!="` operator string. The operator support is dead code today.
* **Why:** Not-equal comparisons are basic control flow. Discovered while verifying improvement #16 (Native Unit Test Blocks): the exact `(if (!= result 5) ...)` example added to the README's "Native Unit Test Blocks" section (and `docs/index.html`) does not lex, so the flagship new-feature example is broken as documented.
* **Impact:** 8/10 (High — silently breaks a documented, common comparison operator).
* **Repro:** `echo '(cli_app (if (!= 1 2) (print "ne")))' > /tmp/t.zero && ./zero /tmp/t.zero` → `{"reason":"Unexpected character: !","line":1,...}`.
* **Fix sketch:** add `ch == '!'` to both character-class checks at zero.go:140 and zero.go:142.
* **Done (2026-07-23):** Added `ch == '!'` / `l.peekChar() == '!'` to the two symbol character-class checks in `lexer()`. Verified `(!= 1 2)` now lexes and the generated Go compiles (`go build`) via `go run zero.go`. Applied directly (trivial, fully-specified two-token diff) after the autonomous `agy --mode accept-edits` delegation call was blocked by the session's permission classifier. Ran the full `tests/*.zero` suite through the transpiler afterward; all pass except `tests/test_include.zero`, which fails for an unrelated pre-existing reason — filed as bug #15.

### 13. `return` in `defun` drops compound expressions
* **Description:** In `generateStatement`, the `"return"` case (zero.go:597-606) does `fmt.Sprintf("return %s", valNode.Value)`. `Node.Value` is only populated for leaf tokens (SYMBOL/STRING/NUMBER) — for a compound expression node like `(+ a b)` or `(call f x)`, `Value` is empty, so the case silently emits a bare `return` with nothing after it. Every other statement/expression case recursively calls `generateStatement(valNode, reqVar, depth+1)`; `return` is the outlier.
* **Why:** Discovered via the same repro as bug #12 — even after fixing `!=` lexing, the README's `(defun add (a b) (return (+ a b)))` example fails to compile in the generated Go (`not enough return values`), because the return value is silently dropped. This affects any `defun` whose return value is not a bare variable or literal (arithmetic, `call`, string concatenation, etc.), a large fraction of realistic function bodies.
* **Why it went unnoticed:** the transpiler exits 0 and produces syntactically-valid-looking Go for simple `(return x)`/`(return "str")` cases; the failure only shows up as a downstream `go build` error on the generated code, which existing example `.zero` files apparently don't exercise.
* **Impact:** 7/10 (High — undermines improvement #6 Function Definitions for any non-trivial return value).
* **Repro:** `(cli_app (defun add (a b) (return (+ a b))) (print (call add 2 3)))` → generated `func add(a string, b string) string { return \n}`.
* **Fix sketch:** replace `valNode.Value` with `generateStatement(valNode, reqVar, depth+1)` in the non-STRING branch, mirroring how other cases (e.g. `call`, binary ops) already recurse.
* **Done (2026-07-23):** Delegated the literal fix-sketch diff to `gemini-3.1-pro-low` via `agy --mode accept-edits`; `git diff` confirmed a real, exactly-matching one-line change. However, verifying it against both named repro cases (`(return (+ a b))` and `(return (call f x))`) surfaced that the sketch's `generateStatement` call was itself wrong for the `call` case: `generateStatement` (unlike `generateStatementRaw`) injects a `//line` directive wrapper for certain heads (`call` included), which corrupts the output when embedded mid-expression inside the `return %s` `Sprintf` — it emitted `return //line ...\n\t\tadd(a, b)`, a bare `return` followed by a floating, uncompiled call, failing with `not enough return values`. Fixed directly by using `generateStatementRaw` instead of `generateStatement` for the recursive call, which has no such wrapping. Added `tests/test_return_compound.zero` covering both the arithmetic (`(+ a b)`) and nested-call (`(call add a b)`) cases; both transpile, `go build`, and run correctly (`add(2,3) == 5`, `add_via_call(4,5) == 9`). Full existing `tests/*.zero`/`examples/*.zero` suite re-run with no new regressions (pre-existing unrelated failures in `test_include.zero` (bug #15), `test_middleware.zero` (missing `TOKEN` env var), and `test.zero` (missing `uuid` Go module) reproduce identically on the pre-fix code). **New finding:** the same `//line`-in-sub-expression corruption exists more broadly — any compound expression recursing through `generateStatement` (not `generateStatementRaw`) whose head is in the wrapped-heads list (e.g. a `call` nested inside a `+`, like `(+ (call f) 1)`) produces the same corrupted output; filed as bug #19 since it's wider than just `return`.

### 14. `(import "pkg")` duplicated/unused in generated `server_test.go`
* **Description:** `generateCode` appends every `extraImports` entry into both `server.go`'s and `server_test.go`'s import blocks unconditionally (zero.go:488 and zero.go:540). Two problems: (a) if a custom import happens to name a package already in the hardcoded default import list (e.g. `(import "strings")`), the generated file declares it twice → Go "imported and not used" / redeclare compile error; (b) even for non-colliding packages, `server_test.go` has no `var _ = pkg.Symbol` suppression the way the default imports do, so a package used only by non-test code (routes/defuns) but not referenced inside any `(test ...)` body makes `server_test.go` fail with "imported and not used" as soon as any `test` block exists alongside any `import`.
* **Why:** Found while verifying improvement #16 (Native Unit Test Blocks) end-to-end with a `.zero` file that combines `(import ...)` with a `(defun ...)` and a `(test ...)` block — a realistic combination now that both features exist.
* **Impact:** 6/10 (Medium-High — breaks the common case of testing a `defun` that relies on an external package).

### 24. No way to write a `defun` with no return value (void function)
* **Description:** `defun`'s codegen (zero.go:389-406) always defaults `returnType` to `"string"` unless a `(type_hint return "...")` is given (zero.go:399-402), and always emits that return type in the generated Go function signature (zero.go:406, `func %s(%s) %s {`). * **Repro:** `(cli_app (defun greet (name) (print "Hello" name)) (call greet "World"))` → transpiles with no error, but `go build` fails with `missing return`. Adding `(type_hint return "void")` instead fails with `undefined: void`.
* **Fix sketch:** special-case the string `"void"` (or introduce a dedicated `(type_hint return "none")` convention) in the `type_hint` handling around zero.go:399-402 so `returnType` becomes the empty string rather than the literal text `"void"`; then adjust the `Sprintf` at zero.go:406 to avoid the resulting double-space when `returnType == ""` (`func %s(%s) {` instead of `func %s(%s)  {`). ### 25. `let` with more than one body statement infinite-recurses instead of erroring
* **Description:** Both `generateStatementRaw` (Go) and `generateJSStatementRaw` (JS) validate a `let` node's arity with `if len(node.Children) < 3 { reportError(...) }` — a lower bound only. The chain-consuming loop right after it requires *exactly* 3 children (`len(curr.Children) == 3`) to treat `curr` as another link in a nested-`let` chain. If the original node has *more* than 3 children (e.g. `(let (var val) stmt1 stmt2)` — a natural mistake, since nothing in the grammar signals `let`'s body must be a single form, unlike `do`, which is variadic), the `< 3` check passes but the loop's `== 3` condition fails on the very first iteration, so the loop body never runs and `curr` is never advanced past the original node. `bodyCode := generateStatement(curr, reqVar, depth+1)` then recurses on the *unchanged* `curr` — i.e. the exact same `let` node — calling straight back into the same code path with an incremented depth, forever, until the depth-1000 safety guard added for bug #5 fires and reports `"AST too deep"` instead of a validation error naming the actual problem.
* **Why:** Found while writing a README.md example for the JS/`web_app` backend (previously entirely undocumented) during a 2026-07-24 documentation pass — a natural first attempt at `(let (count 0) (set count 1) (print count))` (three body-shaped forms after the binding) hit this instead of a normal AI self-correction loop error. Reproduces identically in the Go backend with no JS/`web_app` involvement at all (`(cli_app (let (count 0) (set count 1) (print count)))`), so it's not a JS-backend-specific issue — both backends share the same latent arity gap. Deep, misleading errors like `"AST too deep"` are worse than a normal validation error for the AI self-correction loop this transpiler exists to support (see README's "Why Zero?"): the error text gives no hint that the fix is "wrap multiple body statements in `(do ...)`."
* **Impact:** 6/10 (Medium-High — a very natural authoring mistake produces a confusing, unrelated-looking error with no actionable hint, defeating the transpiler's core self-correction-loop value proposition for this specific case).
* **Repro:** `(cli_app (let (count 0) (set count 1) (print count)))` → `{"reason":"AST too deep: exceeded maximum nesting limit of 1000","line":1,"column":10}` on both the Go and JS (`web_app`) backends, pre-fix.
* **Fix sketch:** tighten both backends' entry check from `len(node.Children) < 3` to `len(node.Children) != 3`, with a clearer message pointing at `do` for multiple body statements.
* **Done (2026-07-24):** Applied the fix-sketch diff to both `generateStatementRaw` and `generateJSStatementRaw` — entry check is now `!= 3` with the message `"let expects (let (var val) body) — wrap multiple body statements in (do ...)"`. ### 39. `-o <dir>` is silently ignored when placed after the input file for the Go/JS backend
* **Description:** `zero.go`'s main flow reads the output directory via `outDir := flag.String("o", "", ...)` and `flag.Parse()`. Go's standard `flag` package stops parsing at the first non-flag argument, so `./zero tests/foo.zero -o /some/dir` — the natural, README-consistent argument order — never registers `-o`: it's silently absorbed into `flag.Args()` as a second positional argument instead, and `*outDir` stays `""`. The Go/JS backend then does `filepath.Join(*outDir, "server.go")` = `"server.go"`, writing the generated server file (and `server_test.go`) into the current working directory instead of the intended output directory.
* **Why:** Found live 2026-07-31 while running a manual `tests/*.zero` fixture sweep for improvement #72: a `zero foo.zero -o $SCRATCH` invocation left a stray `server.go` (its own `package main`/`func main()`) sitting in the repo root, which then broke `go vet ./...`/`go build ./...` with `main redeclared in this block` until manually deleted. `-compile-bc` and `-compile-wasm` already avoid this exact trap via a dedicated `outputFlagAfterInput(args, inputFile)` helper (added for the `-o <exact-file>` semantics those two flags need) that explicitly scans for `-o` positioned *after* the input file — the general Go/JS backend path has no equivalent and silently falls back to the CWD instead of erroring or self-correcting.
* **Impact:** 6/10 (Medium-High — silent, not a crash, and it plants files that can break `go vet`/`go build` for anyone who happens to run the transpiler binary from within its own repo, exactly as happened here; a variant of the same footgun class as the tracked `go build .` golden rule in `improvements.md`'s Working Protocol).
* **Repro:** From the repo root, run `./zero tests/test_wasm_loop.zero -o /tmp/scratch` (any fixture, any writable `-o` target). `server.go`/`server_test.go` land in the repo root (CWD), not `/tmp/scratch`, and `-o`'s value is silently dropped with no warning or error.
* **Fix sketch:** Reuse the existing `outputFlagAfterInput` helper (or a small generalization of it) for the general backend path too: if `flag.Lookup("o")`'s value is empty but `outputFlagAfterInput(os.Args[1:], inputFile)` finds a post-input `-o`, use that as `*outDir`. Add a regression test (or a documented manual repro step) exercising `-o` after the input filename specifically, since the existing test suite likely only exercises the pre-input-file ordering that already works.
* **Done (2026-08-01):** Added the shared `outputDirectory` and `writeArtifact` helpers. Go, JavaScript, and legacy WAT output now accept `-o` after the source path and create nested destination directories; bytecode and SSA-Wasm exact artifact paths receive the same directory creation behavior.
