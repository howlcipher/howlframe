# SELECTION: design rationale and feasibility notes for ticketdesk (Milestone 2)

Author: independent requirements/test author. Frozen with `requirements/` on 2026-10-13. Nothing here weakens a requirement; "hard" items are flagged so the implementer plans for them, not so they are dropped.

## 1. Design rationale

* **Surface sized to the five gates, not to a feature list.** A (HTTP), C (auth), D (validation/errors), G (standalone run), H (DX) each map to named requirement groups (see REQUIREMENTS.md, last section). No endpoint exists only to look impressive; `/v1/me` and `/v1/health` exist because the suite needs a way to identify a token and to poll readiness.
* **One error shape, exhaustive code table (R8).** Ten codes, each tied to exactly one status. The suite asserts the pairing on every error it provokes, so a 400/422 or 401/403 confusion cannot hide.
* **Deterministic order of checks (R3.4).** Unspecified ordering (401 vs 404, 403 vs 415 ...) is the usual source of contradictory black-box tests, so it is specified: route, method, authn, role, existence, ownership, media type, size, JSON syntax, fields.
* **Report all field errors, one entry per field (R7.2).** Costlier than fail-fast but it is what makes "actionable diagnostics" (directive D29-D) testable; order inside `fields` is deliberately unspecified.
* **Opaque cursor pagination over offsets (R6).** Position-based cursors survive deletions (tested) and keep `limit/cursor` semantics honest. Alternative considered: `offset`; rejected (unstable under concurrent deletes, trivially satisfiable and therefore weak evidence).
* **Tokens: `td_` + 64 hex, SHA-256 hex stored, no salt (R11/R12).** Secrets carry 256 bits of entropy so an unsalted fast hash is adequate and makes "a hash, not the secret, is stored" observable from outside (the digest string must appear in the state, the secret must not). Alternatives: salted/KDF hashes (stronger for low-entropy secrets, but not black-box checkable and not offered by the runtime); storing nothing but HMAC (needs a server key, adds state to manage).
* **Bootstrap token never stored (R9, R12).** It lives only in the environment, so rotation is "restart with a new value" (tested in `T-R13-bootstrap-rotation`); it cannot be revoked (`409 conflict`) so an admin lock-out is impossible.
* **Deliberate fault trigger gated by environment (R15).** `X-Debug-Fault: 1` is inert unless the operator sets `TICKETDESK_ALLOW_DEBUG_FAULT=1` (tested inert for unset, `0`, `true`, ` 1`, `11`, `yes`, empty). It must raise a genuine runtime fault so the suite exercises the real fault path (500 body, correlation id, stderr line), not a hand-built 500. Risk accepted: a debug hook exists in the artifact; the gate and the test of its default-off behavior are the mitigation.
* **State in one operator-chosen file, grants scoped to its directory (R1, R2).** Matches how the runtime scopes `file://` stores (`database` plus filesystem read/write coverage) and makes the minimal-grant claim crisp: five grants, each individually removable and tested (`T-R2-missing-*`).
* **Launcher + `HF_RUN_FLAGS` exactly as Milestone 1.** Keeps the independent-suite pattern proven there; runner flags (`--max-request-bytes`, `--access-log`) are the only way tests tune the runtime.
* **Pros/cons of the central architecture choice (JSON file store vs. in-memory only vs. SQLite via `database`).** File store: durable, already in the runtime, whole-file rewrite per mutation (fine at demonstration scale). In-memory: simplest, fails R13. SQL: not required by any selected gate and would add an unrequested dependency. Chosen: file store.

## 2. Feasibility risks for the current runtime (verified in `internal/` and README)

Each item cites what exists today. Items marked **HARD** probably need a narrow, tested language/runtime change per PLAN.md section 4 and directive 7.3 (journal the failing reproduction first).

1. **HARD - port from the environment (R1.2).** `checker.checkGoApp` rejects anything but an integer literal as the `http_server` port (`"Expected integer for port"`), and `OpHttpServerStart` carries the port as a constant string operand. `TICKETDESK_PORT` therefore cannot be honored by pure `.howl`. Options (implementer to evaluate, pros/cons per AGENTS.md): (a) allow a startup-time expression for the port; (b) a runner flag/env override for the listen port; (c) accept a literal and let the launcher recompile (rejected: breaks "build once, run anywhere" and the launcher contract). Not removable: the suite picks free ports.
2. **HARD - raw request body, size and distinguishing errors (R7, R14).** `req.body` is usable only as input to `parse_json` (README). `parse_json` has a hard-coded 10 MiB ceiling (`vm.go` `maxBodyBytes`) raising `LIMIT_EXCEEDED`; the runner has no `--max-request-bytes` yet (PLAN section 4 plans it). The app must tell "too large" from "malformed JSON" in `catch`, which requires the error value to be inspectable (a code or text); `try_let` catches panics generally, but what `err` holds must be checked. Boundary tests (N and N+1 bytes) need exact byte accounting by the runtime, not the app. Also 413 before reading all bytes may reset the client connection: the harness tolerates `BrokenPipe`/`ConnectionReset` when sending and reads the early response.
3. **HARD - JSON value typing (R7.1/R7.2).** `parse_json Any` returns dynamic values; the app must distinguish object vs array vs string vs number vs bool vs null (`[]`, `null`, `true`, `5`, `1.5`, `{}` for `title` ...), strict "no coercion", and reject trailing garbage (`{} x`, two values) and bare `NaN`. I found no type-predicate constructs in `internal/construct` (only `is_nil`); `decodeJSONValue` behavior on trailing data and invalid UTF-8 needs verification. Likely needs a small `type_of`-style primitive.
4. **HARD - string length in code points (R7.2).** `str_len` is a compile-time sugar giving **byte** length (`construct.go`: "byte length via str_split/list_len"). Titles of `é`/CJK/emoji at the 120/4000 boundary (tests `T-R7-length-code-points`) need a code-point length primitive or a UTF-8 aware helper.
5. **HARD - unknown routes and path normalization (R3.2).** `httpreq.Server.ServeHTTP` falls back to Go's `ServeMux`, whose default 404 is plain text, not the JSON error shape; README says there is no catch-all. A `(route "/" ...)` registers a ServeMux subtree pattern and may act as a catch-all, but this is unverified and fragile. Also `cleanRoutePath` applies `path.Clean`, so `/v1//tickets` and `/v1/./tickets` resolve to `/v1/tickets` (the suite deliberately does not test double slashes; trailing slash is preserved, `/v1/tickets/` is distinct and tested as 404).
6. **HARD - safe 500 with correlation id and fault log (R15, R16).** Today a failing handler is recovered in `OpHttpRoute`: the client gets the generic `handlerFailureBody` with no `X-Request-Id`, and the log line is `HTTP handler failure: <error>` without request id/method/path. Either wrap each handler body in `try_let` (the app then builds the 500 and writes the `fault ...` line itself with `stderr`, which adds no newline) or extend the runtime. Faults that escape `try_let` (limits, deadline) still hit the runtime path; the plan's runner changes cover it.
7. **HARD - access log (R16).** No per-request hook exists. `--access-log` must be a runner feature (method, path without query, final status, duration, request id). The status needs the response recorder (`httpResponseRecorder` already tracks `wrote`); the request id must be shared between app and runtime (e.g. the app sets `X-Request-Id` via `res_header` and the runtime logs the header it saw).
8. **HARD - persistence semantics (R13).** `file://` stores are one JSON file rewritten with `os.WriteFile` on every mutation (not temp-file-and-rename), so SIGKILL during a write can truncate state (the suite's SIGKILL test fires after a response, which is safe, but a mid-write kill is a real data-loss risk worth a note in the journal). `store_open` on a **zero-byte** file fails (`json.Unmarshal` of empty input is an error): R1.3 requires zero-byte files to be valid empty state, so the app or runtime must special-case it (tested: `T-R1-empty-data-file-ok`). Corrupt JSON and a directory path surface as `read/decode persisted store` errors that the app must map to exit 65. Records must be dicts (`map[string]any`), so ticket lists/counters need key design (`store_keys` order, id counter record).
9. **HARD - atomicity under concurrency (R13/R17).** Each store operation is locked, but there is no read-modify-write primitive, mutex or compare-and-swap in the construct table. Unique ids and lost-update freedom (`T-R13-concurrent-no-lost-updates`, `T-R17-concurrency-smoke`) need either a runtime lock/atomic counter or a single-writer design. Handlers run on net/http goroutines, so races are real.
10. **Startup exit codes and validation (R1.3).** `exit` exists; startup-time `store`/`do`/`let` forms are accepted by the checker for `http_server`. Reading `env` needs the `environment` grant at startup; the five-grant self-check (R2.2) means probing environment, store open (read), a write probe, and the listener before declaring ready. Exit 77 on missing grants requires the app (or runner) to map `CAPABILITY_DENIED` to 77 with `ticketdesk: capability denied: ...`; today a denied capability inside the runtime ends as a runtime error (exit 1, JSON error object on stderr), which the tests reject. Exit 66/65 distinction needs file-existence probing without extra grants (read covers it).
11. **Request-scoped resource accounting.** `allocations` (`--max-memory-bytes`) is shared by all handlers and "never reclaimed": a long-running server consumes the budget monotonically. The suite passes 4 GiB and does <1000 requests per server, but the guide (`docs/guides/http_api.md`) should state the limit. `--max-instructions` is checked per VM run; confirm it is per request, not per process, or the server will stop after N total instructions.
12. **Header-level details.** `res_header` sets headers before `res_json` (verified: `Header().Set` precedes `WriteHeader`), so `X-Request-Id`, `Allow`, `Location`, `WWW-Authenticate`, `Cache-Control` are feasible. `Content-Type` is fixed to `application/json` by `res_json`. 201/405/413/415 are plain integer statuses (`popCheckedStatus` accepts any int). HEAD requests reach the handler (Go does not auto-route them), so 405 for HEAD is feasible; for HEAD Go suppresses the body, hence the suite checks only status/headers there.
13. **Repeated headers and case.** `req_header` returns one value; Go's `Header.Get` returns the first, which matches R9 ("first value counts"). Header-name case-insensitivity is provided by Go.
14. **Clean-checkout scope (G).** `sha256_hex`, `rand_hex`, `secure_equal` exist since commit `2d8d7945` (construct table). Everything else above must come from `.howl` or narrow runtime changes; no helper program may be used (V3).

## 3. Requirements I consider hard for the language today (do not remove)

In rough order of expected effort: (1) port from environment; (2) runner-enforced body ceiling plus catchable limit error; (3) JSON type discrimination and trailing-garbage rejection; (4) code-point string length; (5) JSON-shaped 404 for unknown routes; (6) per-request safe 500 + correlation id + `fault` stderr line; (7) `--access-log`; (8) zero-byte/corrupt state handling and durable single-file writes; (9) atomic id allocation under concurrency; (10) exit-77 mapping for missing grants at startup. Each is a deliberate probe of "a practical backend on the standalone VM"; where the language lacks the capability, the PLAN section 4 process (failing reproduction first, narrow fix, regression test) applies. None of them may be satisfied by weakening a test.

## 4. Self-check of the suite

The 101 acceptance tests were run against a throwaway Python reference implementation of REQUIREMENTS.md written outside the repository (not committed, not part of the deliverable): 101/101 pass, which shows the spec and tests are mutually consistent. Four hand-made mutants of that reference (raw token stored; `Allow` header missing; ownership check removed; off-by-one body ceiling) each made the relevant tests fail. The DX checker (`dx/check_dx.py`) was run only against a binary built from the freeze commit `52c0c531` (see `dx/BASELINE.md`): 2 of 13 checks pass (the `ok_program` controls), 11 fail, as required before implementation.
