# HowlFrame Benchmark v2

This directory contains Benchmark v2, a suite designed to measure how efficiently an AI or coding agent can arrive at verified, working software in HowlFrame compared with mainstream languages (Go, Python, Node.js).

## What it measures

This benchmark tracks the "AI Write Cost". It measures the effort (time, tokens, repairs) required for an LLM or Agent to produce a **correct, compiler/runtime-verified** solution.

### Tracks

The benchmark is split into two tracks to distinguish raw generation quality from autonomous agent capability:

* **Track A — Language generation benchmark**: A fixed task prompt is given to a model. The model generates source code in a single turn. The code is then built/validated/tested. This evaluates how easy the language is for a model to produce correctly on the first try.
* **Track B — Agentic development benchmark**: A fixed task is given to an autonomous agent. The agent edits files, runs builds/tests, diagnoses failures, and repairs the code iteratively until a verified solution is reached. This evaluates the total work required for an AI coding agent to finish the task.

### Supported Languages and Support Classifications

The benchmark actively supports and runs verifiers for:
- HowlFrame
- Go
- Python
- Node.js

Some tasks are intentionally marked as **Unsupported** for certain languages (e.g. HowlFrame's native state store is unsupported in standard Python without external databases, and HowlFrame lacks general list-sorting currently). The harness explicitly outputs `unsupported` for these, clearly distinguishing them from a model generation failure.

## Runnable Track A Harness

Benchmark v2 includes a fully runnable Track A harness. It does NOT call external APIs, but instead evaluates output files generated by any model/agent to provide unbiased, deterministic verification.

### How to Run a Trial

Use `benchmarks/v2/harness/run_track_a.py`.

```bash
python3 run_track_a.py \
    --task task_01_typed_function \
    --language python \
    --model gemini-1.5-pro \
    --sources /path/to/attempt1.py /path/to/attempt2.py \
    --out benchmarks/v2/results/gemini/python/task_01_1.json
```

**Candidate Attempts / Repairs:**
You can supply multiple paths to `--sources`. The harness will test them in chronological order.
If `attempt1.py` fails, it records the failure, and moves to `attempt2.py`.
If `attempt2.py` succeeds, the trial records:
- `first_pass_success: false`
- `eventual_success: true`
- `repair_attempts: 1`

### Token Count Methodology

The harness uses `tiktoken` with `cl100k_base` if available to count tokens for `final_source_tokens`. If `tiktoken` is not installed, it falls back to a 4-character approximation. The exact counting method used is permanently recorded in the result JSON's `notes` field.

### Result Directory Convention

Save outputs in a nested hierarchy to easily aggregate later:
`benchmarks/v2/results/<model>/<language>/<task>_<id>.json`

## Reference Implementations

Known-good reference implementations for all supported tasks across all supported languages are available in `benchmarks/v2/reference/`. 
**These are meant for testing the verification harness and CI, and MUST NOT be presented as model-generated results.**

## Aggregating Trials

Do not draw strong conclusions from a single run due to LLM non-determinism. Run 5-10 independent trials.

To aggregate results, use the included `aggregate.py`:

```bash
python3 benchmarks/v2/harness/aggregate.py --results-dir benchmarks/v2/results/
```

This aggregates all JSON files recursively and outputs a Markdown table summarizing:
- 1st Pass % and Eventual % Success rates
- Median Repair attempts (with Min/Max)
- Median Elapsed Time (with p90 if sample size >= 10)
- Median Tokens
- Capability testing results

### How Capability Tests Work

Task 08 verifies how the runtime reacts to a capability denial (e.g., trying to write to the filesystem without permission). 
The harness runs the generated code in a restricted capability environment. If the code successfully catches the panic (via `try_let` in HowlFrame) and gracefully outputs "Access Denied", the capability test passes and is recorded in the aggregation.

## What Benchmark v2 still does NOT measure automatically

- Track B agent interactions and automatic API fetching. (You must run the model separately and feed the outputs to the harness).
- Automated generation of token API costs.
- Fully isolated docker containers for third-party languages (commands are run locally via `subprocess`).

## Historical Data

Benchmark v1 (which measured just tasks A, B, and C manually) is retained in `benchmarks/language_write_cost` and documented in `docs/language_write_cost_benchmark.md`.
Do not present reused historical timings as fresh independent measurements for Benchmark v2.
